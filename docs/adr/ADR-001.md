# ADR-001 — SQLite + `node:sqlite` for the local alpha

**Date:** recorded at alpha architecture decision
**Status:** Accepted

## Context

The alpha must run as a **local, single-process, zero-additional-software** platform. We evaluated Supabase/Postgres vs pure-SQLite. The blueprint asked for "open-source, no-extra-software," and we wanted an investigator to clone the repo, `npm install`, and play with no database daemon, no connection config, and no cloud account.

## Decision

I chose SQLite via Node's built-in **`node:sqlite`** (`DatabaseSync`) for the alpha data layer. The schema lives in `src/shared/db.js` (WAL journaling, foreign keys on), and a thin wrapper in `src/shared/database.js` exposes a small repository API (`getDb`/`setDb`) so callers never touch raw SQL.

Key implementation choices:
- File DB at `data/detective.db` (overridable via `DB_PATH`).
- Tests inject an isolated `:memory:` instance through `setDb()`.
- Storage namespace bug fixed via per-case id namespacing (see ADR-004).

## Consequences

**Positive**
- Zero dependencies and no daemon — the whole platform boots offline with one process.
- Node 22 ships `node:sqlite`, so no native build step.
- `node:sqlite` is fully open source.
- In-memory DB makes integration tests fast and hermetic (`tests/services.test.js`).

**Negative / tradeoff**
- Single-writer; not horizontally scalable under heavy concurrent load.
- No hosted managed infra (no Supabase auth, realtime, or edge functions).
- `DatabaseSync` is synchronous — fine for a local alpha, but blocking I/O if we grow.

## Path to swap

`src/shared/database.js` is the only choke point routes/services use. To go Postgres/Supabase, I replace `./db.js` internals behind the same `getDb`/`setDb` API; no caller changes. The leftover `pg` dependency in `package.json` and `src/shared/redis.js` are transitional and not wired into the running request path today — they are staging for this swap, not live services.
