# ADR-004 — Truth-Before-Language: canonical, knowledge, and presentation state are separate; per-case id namespacing

**Date:** recorded at alpha architecture decision
**Status:** Accepted (non-negotiable platform invariant)

## Context

The fundamental risk of an AI detective game is that the model "un-mysterizes" the mystery: it leaks the culprit, contradicts established facts, or invents new truth mid-session. If the LLM could alter ground truth, the puzzle stops being fair and the platform stops being a game. We also generate multiple cases that reuse the same short local ids (e.g. `char_s0`, `fact_motive`), which would collide if stored naively in shared tables.

## Decision

I enforce **Truth-Before-Language**: canonical facts are immutable in the database, and the LLM may **only** touch the presentation layer, always validated against canonical state. Concretely, the schema splits three layers:

1. **Canonical state (truth)** — `facts` tables with `canonical_value`, `visibility`, `category`; `events` with canonical start/end times; `characters.is_culprit`, `cases.culprit_id`, `cases.canonical_hash` (SHA-256 of the manifest). This is the ground truth.
2. **Knowledge state (what each NPC knows)** — `character_knowledge` maps character → fact with `certainty`, `source`, `can_disclose`. A character's permitted knowledge slice is derived from this.
3. **Presentation state (what the LLM said)** — `ai_calls` telemetry and interview snapshots/transcripts. The LLM output is validated against canonical state before it reaches the player (`NpcOrchestrator._validate`).

**Runtime enforcement points**
- **NPC responses:** `NpcOrchestrator` builds a bounded prompt from `can_disclose` facts, and `_validate()` strikes any `disclosed_fact_ids` not in the character's permitted slice, flagging the response `rejected` and softening the spoken text.
- **Case generation:** `CaseGenerator` assembles ground truth first; anything failing `CaseValidator` is rejected and never published.
- **Immutable manifests:** `CaseRepository` treats published cases as versioned, immutable documents.

**Per-case id namespacing** — the DB child tables (`characters`, `facts`, `events`, `evidence`, `lies`, `locations`, `relationships`) key on `id` alone, so generated cases reusing local ids would collide. `CaseRepository` namespaces every stored child id as **`<caseId>#<localId>`** on save and strips the prefix back on load, so in-memory manifests always use short, stable local ids (see `_ns` / `_unns` in `src/services/case-repository.js`). This also satisfies the `evidence.id` foreign-key from `discoveries`.

## Consequences

**Positive**
- Fair-play is structurally guaranteed: the truth cannot drift regardless of what the model does.
- Multiple generated cases coexist in one database without id collisions.
- An admin can diff canonical fact values against anything the LLM ever said (ADR-004 fulfills MVP criterion 7 in the GDD).

**Negative / tradeoff**
- LLM output must be schema-constrained (structured JSON) and validated — more plumbing than free-form chat.
- Detecting "model successfully lawyered around an unpermitted disclosure" is heuristic, not provable; the validation catches declared `disclosed_fact_ids` and referenced evidence, and softens text on rejection.

## Path to adjust

The split is a data-model invariant, not a knob. New layers (e.g. player-visible vs secret narration) should preserve the same rule: write canonical state once, present through a validated projection.
